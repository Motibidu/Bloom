## 인증 / 보안

### JWT 이중 토큰 + 토큰 재사용 감지

보안을 고민하다 보면 액세스 토큰 하나만 쓰는 구조가 얼마나 취약한지 금방 보인다. 토큰이 탈취되면 만료될 때까지 공격자가 자유롭게 쓸 수 있고, 그렇다고 만료 시간을 짧게 잡으면 사용자가 자꾸 로그아웃된다. 이 딜레마를 해결하기 위해 액세스 토큰(15분)과 리프레시 토큰(7일)을 분리했다.

리프레시 토큰을 DB에 저장할 때 평문 그대로 넣으면 DB가 털렸을 때 모든 세션이 위험해진다. SHA-256 해시 후 저장하는 방식을 선택한 이유다. 그런데 여기서 한 가지 더 고민이 생겼다. 리프레시 토큰 자체가 탈취되면 어떻게 되는가. 공격자가 먼저 사용하고, 정상 사용자가 나중에 사용하려 할 때 이미 폐기된 토큰이라는 응답을 받게 된다. 이 상황을 단순 오류로 처리하면 공격을 감지할 수 없다.

토큰 재사용 감지(Reuse Detection)를 구현한 이유가 여기 있다. 이미 폐기(revoked)된 토큰으로 재사용 시도가 들어오면, 단순 거절이 아니라 해당 유저의 모든 세션을 즉시 폐기하고 경고 로그를 남긴다. 탈취 사실을 인지하는 즉시 피해를 차단하는 구조다.

### 카카오 OAuth 2.0 소셜 로그인

50~60대 사용자를 대상으로 서비스를 만들면서 가장 먼저 부딪힌 문제가 회원가입 이탈이었다. 이메일·비밀번호를 직접 입력하는 과정이 이 연령대에게는 진입 장벽이 된다. 카카오 로그인을 붙이기로 결정한 배경이다.

Authorization Code Flow를 직접 구현하면서 예상치 못한 케이스가 나왔다. 카카오로 가입하려는 사용자가 이미 동일한 이메일로 이메일 가입을 한 경우다. 두 계정을 별개로 만들면 사용자는 자신이 이미 가입되어 있다는 사실을 모른 채 중복 계정을 갖게 된다. 카카오 이메일과 기존 계정 이메일을 대조해 자동으로 계정을 연동하는 처리를 추가한 이유다.

신규 카카오 가입자는 닉네임이 없는 임시 계정 상태로 시작한다. 온보딩을 완료해야 정상 계정이 되는 2단계 플로우다. 이 구조 덕분에 서비스 진입 문턱은 낮추면서 필수 정보(닉네임, 생년)는 반드시 받을 수 있었다.

### 이메일 인증 코드 회원가입

회원가입 시 이메일 소유 여부를 검증하지 않으면 타인의 이메일로 가입하는 어뷰징을 막을 수 없다. 특히 50~60대 사용자가 실수로 이메일을 잘못 입력했을 때 나중에 비밀번호 찾기조차 안 되는 상황이 생긴다.

인증 코드 생성 시 `Random` 대신 `SecureRandom`을 쓴 이유는 예측 가능성 때문이다. `Random`은 시드가 추측 가능해 코드를 미리 계산하는 공격이 이론적으로 가능하다. 코드 재발송 시 기존 코드를 먼저 삭제하는 처리도 넣었다. 여러 코드가 동시에 유효한 상태가 되면 가장 오래된 코드로도 인증이 통과되는 허점이 생기기 때문이다.

## 성능 최적화

### 피드 조회 N+1 문제 — 벌크 쿼리로 해결

피드 화면을 처음 만들었을 때 로컬에서는 문제가 없었다. 데이터가 적었기 때문이다. 그런데 구조를 들여다보니 체크인 목록을 가져온 뒤 각 체크인마다 좋아요 수, 댓글 수, 리액션 집계 쿼리가 개별로 나가고 있었다. 체크인이 20개면 쿼리가 60번 이상 나가는 구조였다. 사용자가 늘고 피드에 데이터가 쌓이면 응답 시간이 선형으로 늘어날 게 뻔했다.

fetch join을 먼저 검토했다. 하지만 좋아요·댓글은 단순 조인이 아니라 집계(COUNT)가 필요했고, JPA에서 컬렉션 fetch join과 페이지네이션을 함께 쓰면 Hibernate가 전체 데이터를 메모리에 올린 뒤 애플리케이션 레벨에서 잘라낸다는 경고가 뜬다. 데이터가 많아질수록 오히려 더 위험한 구조였다.

결국 선택한 방법은 checkinId 목록을 먼저 확보하고, IN절 벌크 쿼리 3개(좋아요 수, 댓글 수, 리액션)로 일괄 집계하는 방식이다. 쿼리 수가 N×3에서 고정 3으로 줄었다. 피드에 체크인이 몇 개든 쿼리 수는 변하지 않는다.

### 커서 기반 페이지네이션

피드 무한 스크롤을 처음에는 offset 방식으로 구현하는 게 가장 빠르다. 그런데 offset은 구조적인 문제가 있다. `OFFSET 1000`이면 DB가 앞의 1000개를 읽고 버린 뒤 그다음을 반환한다. 데이터가 쌓일수록 뒤 페이지로 갈수록 느려진다. 또 피드에 새 게시물이 올라오면 offset이 밀려 같은 게시물이 두 번 보이거나 게시물이 건너뛰어지는 현상도 생긴다.

커서 기반으로 바꿨다. 마지막으로 받은 체크인 ID를 커서로 삼아 `WHERE id < cursor` 조건으로 다음 페이지를 조회한다. ID 컬럼에 인덱스가 있으므로 데이터 양에 관계없이 일정한 속도를 보장한다. limit+1개를 조회해서 다음 페이지 존재 여부(hasMore)를 판단하는 방식도 함께 적용했다.

### UTC 저장 / KST 변환 — 시간대 처리 설계

처음에 created_at을 서버 시간대 기준으로 저장하면 배포 환경이 바뀌거나 서버가 다른 시간대에 있을 때 데이터가 뒤틀린다. 모든 시각은 UTC로 저장하고, 오늘 KST 날짜 범위가 필요할 때만 UTC로 역산해서 쿼리하는 방식을 선택했다.

예를 들어 오늘 KST 2025-05-23의 활동을 조회하려면 UTC 기준 2025-05-22 15:00:00 ~ 2025-05-23 14:59:59 범위로 쿼리한다. 서버가 어느 시간대에 있어도 항상 정확한 "오늘 KST"를 보장한다.

## 파일 업로드

### AWS S3 Presigned URL 3단계 업로드

처음 구현 방식은 클라이언트가 서버에 파일을 올리면 서버가 S3에 전달하는 구조였다. 단순하지만 문제가 있다. 사진 파일은 수 MB에 달하는데 모든 파일이 서버 메모리를 통과한다. 사용자가 동시에 업로드하면 서버 메모리와 대역폭이 빠르게 소모된다. 서버가 병목이 된다.

S3 Presigned URL을 선택한 이유다. 서버는 S3에 직접 업로드할 수 있는 서명된 URL만 발급하고, 실제 파일은 클라이언트가 S3에 직접 올린다. 서버는 파일을 한 바이트도 처리하지 않는다.

한 가지 보안 이슈가 있었다. 발급한 URL의 경로(objectKey)를 클라이언트가 임의로 바꾸면 다른 사용자의 폴더에 파일을 올릴 수 있다. 체크인 등록 시 서버에서 objectKey가 반드시 `checkins/{userId}/`로 시작하는지 검증하는 이유다. 클라이언트가 경로를 조작해도 서버에서 걸러낸다.

## 알림 시스템

### FCM + SSE 이중 알림 구조

같은 서비스를 웹 브라우저와 앱(WebView) 두 경로로 제공하면서 알림 방식이 달라야 했다. 브라우저는 앱이 실행 중일 때만 연결을 유지할 수 있어 SSE(Server-Sent Events)가 적합하다. 반면 앱은 백그라운드 상태에서도 알림을 받아야 하므로 FCM(Firebase Cloud Messaging) 푸시가 필요하다. 하나로 통일하면 어느 한쪽에서 알림을 받지 못하는 사용자가 생긴다.

FCM 발송을 `@Async`로 비동기 처리한 이유는 동기로 처리하면 FCM 서버 응답을 기다리는 동안 좋아요·댓글 등 메인 트랜잭션이 블로킹되기 때문이다. 알림 발송 실패가 본 기능의 실패로 이어지는 구조는 피해야 했다.

FCM 토큰이 만료되거나 앱을 삭제한 경우 FCM 서버가 `UNREGISTERED` 오류를 반환한다. 이 오류를 감지해 해당 토큰을 자동으로 삭제하는 처리도 넣었다. 쌓인 만료 토큰에 계속 발송을 시도하면 불필요한 외부 API 호출이 누적된다.

## 아키텍처 / 설계

### 도메인 기반 패키지 구조

초기에 레이어 기준(controller, service, repository)으로 패키지를 나누면 파일이 적을 때는 편하다. 그런데 도메인이 늘어날수록 하나의 레이어 폴더 안에 서로 관련 없는 파일들이 뒤섞인다. 체크인과 알림이 같은 service 폴더에 있으면 어떤 파일이 무엇과 연관되는지 파악하기 어려워진다.

도메인 기준으로 패키지를 나눈 이유다. auth, user, checkin, comment, like, follow, block, family, notification, report — 각 도메인이 자신의 controller, service, repository, entity, dto, exception을 모두 품는다. 새 도메인을 추가할 때 기존 코드를 건드리지 않고 폴더 하나를 새로 만들면 된다. 도메인별 비즈니스 예외도 해당 도메인 폴더 안에 두고, GlobalExceptionHandler 한 곳에서만 HTTP 응답으로 매핑한다.
